# TTS Prompt-Design Benchmarks

A Docker-only workbench for comparing open-source text-to-speech models that can
**design a speaker from a natural-language prompt** ("a raspy elderly man,
speaking slowly and kindly"). Every model is served with
[vLLM-Omni](https://github.com/vllm-project/vllm-omni). A React frontend lets you
start one model at a time, generate clips, and compare them side by side with
clips other models made earlier.

```
 browser ──► frontend (React, nginx)                         :3000
                 │  /api/* proxied
                 ▼
            controller (FastAPI, Docker API, clip library)   :8090
                 │  creates / stops containers via docker.sock
                 ▼
   ttsbench-backend-<model>  (vllm/vllm-omni + entrypoint)   :81xx
        /models  ◄── read-only mount of the models volume (weights live here only)
```

| Component | Image | Role |
|---|---|---|
| `frontend` | `ttsbench/frontend` | React app for model switching, generation and side-by-side listening |
| `controller` | `ttsbench/controller` | Model registry, backend lifecycle, generation, clip library |
| `backend-image` | `ttsbench/vllm-omni:<tag>` | Thin wrapper over `vllm/vllm-omni`. No weights inside. Started on demand |
| `downloader` | `ttsbench/model-downloader` | One-shot: fills the models volume from Hugging Face |
| `bench` | `ttsbench/controller` | One-shot: runs a prompt suite across models and writes a CSV |
| `mock-backend-image` | `ttsbench/mock-tts` | Optional GPU-free fake backend for UI work |

## Requirements

- Docker with Compose v2.24 or newer (uses `additional_contexts: service:`).
- An NVIDIA GPU and the NVIDIA Container Toolkit for real backends.
- Disk for the vLLM-Omni image (about 9 GB) and the model weights.

## Quick start

```bash
make env                                 # creates .env
make build                               # builds all images
make download M=qwen3-tts-voicedesign    # weights go into the models volume
make up
```

Open http://localhost:3000.

## Workflow

Compute is assumed to fit one model at a time, so the UI is built around
filling one model's column, then switching.

1. **Start a model** in the Models panel. Starting another one stops the
   current backend first. Loading progress and logs show in the panel.
2. **Add samples.** A sample is a voice prompt plus a line of text. Add them one
   at a time, or import a suite from [benchmarks/](benchmarks/).
3. **Generate.** Use "Add & generate" for a new sample, "Generate" in a cell, or
   "Fill N missing" to generate every sample the running model has no clip for yet.
4. **Switch models and repeat.** Clips from stopped models stay in the grid.
5. **Compare.** Each row has one column per model. "Play row" plays the latest
   clip from every visible column back to back. Column chips hide or show models.
   Earlier takes stay under "+N earlier".

## Clip library

Every generated clip is stored by the controller on the `ttsbench-data` volume:

```
/data/library.db                         SQLite index of samples and clips
/data/audio/<model-key>/<clip-id>.wav    audio files, grouped by model
```

Each clip records the model key, Hugging Face repo, backend image, the exact
`/v1/audio/speech` request, latency, audio duration, real-time factor and sample
rate. Samples are unique by voice prompt and text, so the same pair generated by
different models, or by the CLI benchmark, lands in the same row.
"Export CSV" downloads the whole index.

## Models

Models are declared in [config/models.yaml](config/models.yaml). The registry maps
the voice prompt and text onto each model's `/v1/audio/speech` request, because
models expose voice design differently.

| Key | Hugging Face repo | Voice prompt goes to | Status |
|---|---|---|---|
| `qwen3-tts-voicedesign` | Qwen/Qwen3-TTS-12Hz-1.7B-VoiceDesign | `instructions` with `task_type=VoiceDesign` | documented |
| `breeze-tts-2` | BreezeBlue/Breeze-TTS-2 | `instructions` without `ref_audio` | documented |
| `omnivoice` | k2-fsa/OmniVoice | `instructions` | experimental |
| `voxcpm2` | openbmb/VoxCPM2 | parenthesised prefix of `input` | experimental |

### Adding models from the UI

"+ Add model" in the Models panel takes a Hugging Face repo id and checks it
against the backend image in use before anything is downloaded. The check runs
inside that image, so it reflects exactly the pinned vLLM-Omni version:

1. **Found on Hugging Face.** Size, licence and gating come from the Hub API.
2. **Resolves to a vLLM-Omni pipeline.** This calls vLLM-Omni's own
   `resolve_omni_config`, the same path `vllm serve --omni` takes. Only config
   files are fetched.
3. **Served through `/v1/audio/speech`.** vLLM-Omni's TTS adapter detection must
   recognise one of the pipeline stages.
4. **Auxiliary repos.** Some models load extra repos at runtime, such as
   MOSS-VoiceGenerator's audio tokenizer. The check scans vLLM-Omni's code for the
   detected model family, plus the model config, for those repos. They download
   with the model into `/models/.hf-cache`, where backends find them offline.
5. **Voice prompt support.** This maps the detected adapter to how it takes a
   voice description: documented voice design, `instructions` that are forwarded
   but unverified for design, a text prefix, or none.

Only models that pass the first three checks can be added. The dialog suggests a
request template and serve arguments for the adapter, and both can be edited.
The model is then saved to `/data/models.custom.yaml` on the data volume and its
weights download in a one-shot downloader container, with progress in the panel.

Results are cached per backend image. After changing `VLLM_OMNI_TAG`, click a
model's version badge to re-check it. Built-in models can be verified the same
way, and missing weights can be downloaded from their card.

To add a model by hand instead, add an entry to the registry with a unique
`host_port`, download it, and restart the controller with
`docker compose restart controller`.

## Model weights and volumes

Weights are never baked into an image. They live in one place, mounted read-only
into each backend at `/models/<org>/<repo>`:

- By default this is the Docker named volume `ttsbench-models`.
- To use an existing host directory, set `TTSBENCH_MODELS_SOURCE=/abs/path` in
  `.env`. It must use the `<org>/<repo>` layout.

Backends run with `HF_HUB_OFFLINE=1`, so a missing file fails fast instead of
downloading. Override per model with `env:` in the registry.

| Volume | Contents |
|---|---|
| `ttsbench-models` | Model weights |
| `ttsbench-backend-cache` | vLLM / torch compile caches, for faster restarts |
| `ttsbench-data` | Clip library, UI-added models and cached verifications |

## APIs

**Each backend** exposes vLLM-Omni's OpenAI-compatible API on its `host_port`,
bound to `BACKEND_BIND` (localhost by default):

```bash
curl -s localhost:8101/v1/audio/speech -H 'Content-Type: application/json' -o out.wav -d '{
  "model": "Qwen/Qwen3-TTS-12Hz-1.7B-VoiceDesign",
  "task_type": "VoiceDesign",
  "instructions": "A cheerful young woman with a slight rasp",
  "input": "Good morning! Ready to get started?"
}'
```

**The controller** on port 8090 (also at `/api` behind the frontend) has
interactive docs at http://localhost:8090/docs.

| Method | Path | Purpose |
|---|---|---|
| GET | `/models` | Registry, backend state, download progress, verification and clip counts |
| GET | `/system` | Backend image and vLLM-Omni version |
| POST | `/catalog/verify` | `{repo, refresh?}` checks a repo against the pinned vLLM-Omni |
| POST | `/catalog/models` | Adds a verified model and starts its download |
| DELETE | `/catalog/models/{key}?delete_weights=` | Removes a UI-added model |
| POST / DELETE | `/downloads/{key}` | Start or cancel a weights download |
| POST | `/backends/{key}/start?wait=true` | Spin up a backend |
| POST | `/backends/{key}/stop` | Remove a backend container |
| GET | `/backends/{key}/logs` | Container log tail |
| GET / POST | `/samples` | List samples with their clips, or add one |
| POST | `/samples/{id}/generate` | `{model, params?}` generates a clip on a running backend |
| POST | `/synthesize` | `{model, prompt, text, ...}` finds or creates the sample, then generates |
| GET | `/clips?model=&sample_id=` | Query clips |
| GET | `/clips/{id}/audio` | Audio file |
| DELETE | `/clips/{id}`, `/samples/{id}` | Remove a clip, or a sample with its clips |
| GET | `/clips.csv` | Export the library |
| GET / POST | `/suites`, `/suites/{name}/import` | Load benchmark suites as samples |

## Benchmarking

```bash
make bench     # or: docker compose run --rm bench /benchmarks/suite.yaml --models qwen3-tts-voicedesign
```

[benchmarks/suite.yaml](benchmarks/suite.yaml) lists voice-prompt and text cases.
Each model is started, warmed up, run through every case, then stopped. A CSV
goes to `/data/bench/` and every clip lands in the library, so the results show
up in the frontend's grid.

## Configuration notes

- **One GPU:** `EXCLUSIVE_BACKENDS=true` (default) stops other backends before starting one.
- **Warm-up:** a backend is reported ready only after one discarded request, so the
  first stored clip is not a cold start. Disable with `BACKEND_WARMUP=false`.
- **Remote access:** set `FRONTEND_BIND=0.0.0.0`. The browser only talks to the
  frontend, which proxies the API, so the controller can stay on localhost.
- **Without a GPU:** `docker compose --profile tools build mock-backend-image`, then set
  `BACKEND_IMAGE=ttsbench/mock-tts:latest` and `BACKEND_GPUS=none`.
- **Security:** the controller mounts `/var/run/docker.sock`, which grants root-equivalent
  access to the host. It binds to localhost by default. Do not expose it publicly.
- **Frontend development:** `make dev` serves the React app with hot reload on
  port 5173, proxying `/api` to the running controller.
